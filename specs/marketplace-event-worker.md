# Direct EventBridge-to-SQS lifecycle worker

Scope, 2026-10-29: a real SDK-backed consumer and strict configuration preflight,
tested offline against botocore models. No queues, roles, rules, permissions,
subscriptions or paid resources are created. No public webhook, metering call,
provisioner or deployed event-authenticity claim is introduced.

Pin seller, IAM consumer role, us-east-1 standard queue URL/ARN, default-bus rule,
processing DLQ and delivery DLQ. Reject root/wrong account/wrong assumed role.
Read actual queue attributes, DescribeRule and ListTargetsByRule; require an
enabled exact source/account/region/lifecycle pattern, single direct queue target,
unchanged event body, delivery DLQ and bounded retry profile. Require the narrow
queue send-policy profile generated by this module: EventBridge with exact
SourceArn/SourceAccount, and an explicit deny for other SourceArns, including
missing source context. Do not write policies or broaden one to make a test pass.
Processing DLQ accepts redrive only from this queue; delivery DLQ has the pinned
rule send profile. Require SQS-managed encryption and bounded retention/visibility
attributes. This is a deliberately narrow supported deployment profile, not a
general IAM-policy theorem prover. Trusted account administrators and an audited
actual deployment remain part of the security boundary.

Revalidate before polling and after a returned message before mutation. Receive
one original EventBridge JSON body, with 10-second long polling and 60-second
visibility. Use SDK HTTP read timeout longer than the long poll. Check message
shape/body bound/MD5, reject duplicate JSON keys/nonfinite constants, and route
only supported events through the existing positive/negative reducers. MD5 checks
transport integrity, not producer identity. Never treat a JSON source field as
a signature; the verified AWS queue/rule path is required, and real service-origin
and IAM tests remain a release gate. Custom EventBridge v2 system metadata does
not establish authenticity for this classic default-bus deployment.

Delete the received message only after the reducer transaction commits. A delete
failure leaves committed event state for idempotent redelivery. Invalid messages,
DB failures and configuration changes never get a success acknowledgement. Do
not log bodies, receipt handles, raw responses or credentials. Redrive and alerts
must be validated in deployment; the worker does not silently replay DLQs or
infer health from an approximate queue count. Preserve customer data and charges.

Tests use actual SDK models/Stubber for all control and receive/delete calls,
and real SQLite reducers. Cover identity, rule/policy/target/DLQ substitution,
body transformations, duplicate JSON and checksum, invalid event, DB failure,
delete failure/redelivery, empty poll, negative events, configuration change
while polling, and refusal before any receive when the boundary is not verified.
A bounded CLI consumes configured existing infrastructure through the normal AWS
credential chain; no fabricated live configuration or long-term keys are shipped.

## Implemented profile and local evidence

marketplace_event_worker.py provides the actual SDK factory, preflight, one-poll
consumer and bounded operator CLI. The rule pattern scopes license updates and
revocations to the configured product ID/code. Agreement-end events allow the
configured product ID or an absent product ID, retaining the negative reducer's
pre-registration stop behavior without accepting foreign positive licenses.
The $or/exists pattern must still be tested against actual AWS delivery before
production; no created rule or AWS TestEventPattern result is claimed here.

Further primary references:

- https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-create-pattern-operators.html
- https://docs.aws.amazon.com/eventbridge/latest/ref/events-structure.html
- https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-archive.html

The classic event metadata reference documents service-reserved aws. sources.
The raw target, pinned policies and TLS/SigV4 SDK path are therefore necessary
parts of the proposed origin boundary; JSON source/MD5 checks in isolation are
still insufficient. Real effective IAM and producer/route validation are not
replaced by successful Stubber responses or a policy string comparison.

Archive replay adds replay-name. Validate it against the current SDK replay-name
pattern/length, then exclude only that field from the durable business-event
digest. Other fields, identities and cross-kind changes remain conflicts. Old
digests are never rewritten: a pre-change record that included replay metadata
may require explicit reconciliation; a mismatch fails closed. Already-recorded
normal events keep the same digest. Positive and negative archive replays do
not undo cancellation or create additional event state.

Thirty-three new tests pass, complete Python suite **253 passed locally**.
They use actual STS/SQS/EventBridge botocore models and actual SQLite reducers.
Coverage includes both role and control-plane substitutions, all three input
transformation forms, separate DLQ controls, missing receipt identity, strict
JSON/checksum, empty receive, database failure, delete failure followed by a new
receipt handle, negative stops, archived positive/negative replay, legacy digest
preservation and sanitized CLI credential/configuration failure. An initial
paginated-target fixture incorrectly used an empty Targets list, which the SDK
model rejects; corrected it to a valid nonempty paginated response, then verified
that the worker rejects it. No actual AWS event was used by these tests.

Run the bounded CLI only after infrastructure is separately approved/deployed,
its effective IAM/source checks pass, and a private runtime configuration has
been populated with actual observed resource identifiers:

```sh
python scripts/runix/marketplace_event_worker.py --config /absolute/private/worker.json
```

Required config fields are the six EventTransport fields plus database,
seller_account, product_code and product_id. No real/sample live configuration
or credentials are shipped. The CLI performs one verified-profile poll, prints
only boolean processing results, and never creates/changes infrastructure.
Delete requested is not a guarantee of exactly-once delivery; state remains
idempotent even after a successful SQS delete response. Dead-letter redrive,
monitoring and missed-event reconciliation are not automated by this worker.
